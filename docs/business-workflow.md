# 业务需求模块：第一版流程草案

状态：依据访谈整理。产品边界已确认；以下界面命名、状态拆分和按钮细节是待原型验证的建议，不代表功能已实现。

## 通用流程与首版范围

主流程面向软件开发任务，首版默认只提取并实现前端部分。后续后端、客户端和跨端需求沿用相同流程，按实现单元关联职责、仓库、依据、验收条件与依赖。

仓库不等于开发端：一个仓库可以包含多个端，一个端可以涉及多个仓库。实现单元是工作范围的划分，不默认对应独立 worktree；同一需求内共享仓库时仍需协调写入。

各端差异通过项目配置及流程模板表达，例如所需资料、Agent 指令、skills、测试命令与交付方式。首版的接口就绪条件是前端流程默认值，后续不作为后端或客户端的统一限制。

## 首次配置与后续增量

设置提供「数据源」「代码仓库」「Agent 配置」三个入口。先支持 Codex CLI 和本机执行。

数据源使用表单添加：名称、飞书地址、资源与工作表选择、负责人字段、本人匹配值、筛选条件及刷新设置。读取后提供字段预览和连接验证。根据地址识别资源类型，实际支持范围待接入验证。

没有数据源时展示配置入口，也可使用明确标记的示例数据体验流程。真实地址可随时添加，不将真实业务地址写死在程序中。示例任务不可执行真实部署或外部状态修改。

后续可以新增、编辑、暂停和验证数据源。编辑地址或字段后重新验证映射；同步异常不删除已有任务。相同来源重复拉取不重复建任务，不同来源指向同一需求时允许关联。

代码仓库通过平台授权发现，选择代码根目录后扫描 Git remote 并匹配。未匹配仓库提供「选择已有目录」「克隆到所选目录」。远程身份可同步，本地路径按机器保存。

Agent 配置自动发现并批量纳管 rules、skills 和角色定义。导入项纳入版本管理；外部插件管理项可仅引用。展示全局、项目及本次任务的有效配置来源，不能将仅已发现的配置标成已加载。

## 从需求到执行

1. **发现**：从数据源筛出分配给用户的需求，显示来源、更新时间和同步异常。
2. **整理**：点击「开始需求」，读取关联资料，生成实现范围、验收条件、引用与待确认问题；首版默认提取前端功能和交互。
3. **补齐**：用户添加 ApiFox、Figma 或其他依据；缺少必要协议时进入等待。纯前端需求无需等待接口。
4. **调研**：推荐仓库并只读分析，输出方案、跨仓库依赖与需要用户决定的事项。
5. **确认**：用户审阅实现依据、仓库、基准分支、方案及配置清单，点击「确认并开始」。确认前不修改业务代码。
6. **执行**：按需克隆并建立任务 worktree，依次或在依赖允许时并行执行实现、审查、修改、自测。
7. **验收**：汇总变更、检查证据和未验证项。检查未执行、失败和通过分别显示。
8. **交付**：用户通过按钮提交、推送、部署；每个动作有独立结果，失败可单独处理。

建议将任务生命周期、Agent 运行状态、Git 状态和部署状态分别保存。例如「自测通过但推送失败」不能被一个笼统的「完成」覆盖。

## 用户操作界面

需求详情建议提供「依据与方案」「执行」「变更与验证」「交付」「决策与交接」。无需依靠聊天触发日常推进。

- **确认并开始**：固定本轮依据与规则版本，在选定仓库中执行。
- **暂停／继续**：明确是否已经停止进程；有仍在执行的操作时不能宣称已暂停。
- **补充变更**：展示新旧依据差异、关联需求与影响仓库，确认后创建新执行轮次。
- **提交**：先查看各仓库差异、选择文件与提交说明，再执行；不默认带入无关本地修改。
- **推送**：显示仓库、分支、目标远程及待推送提交；分别记录多仓库结果。
- **部署**：显示 DevHub 目标、环境与分支或提交。请求受理、构建成功和部署成功分别显示；通知沿用 DevHub 配置。
- **保存交接**：记录任务阶段、各仓库分支与提交、未完成项、依据版本和下一步；同步外部代码仍遵守用户触发推送的边界。

部署细节读取现有 DevHub 配置；缺少必要配置时进入设置，不要求用户改用对话执行。

## 会话入口与历史

导航预留「会话」入口；需求详情提供关联会话。可直接提问，也可选择仓库或任务作为上下文，查看历史、继续会话，并定位关联的执行记录。

会话与执行分开：问答可解释方案和结果，准备修改时形成任务或候选变更，仍需经过确认。结构化按钮继续承担提交、推送、部署等操作，不要求用户通过聊天操作。

历史保留消息与资料引用。将会话结论纳入当前依据或长期记忆需要显式确认。调用时按任务与阶段选取相关上下文，完整历史可查，不默认全部加载。

底层 CLI 会话能否持久化、原生续聊、取消与恢复，在执行器接入时验证。不能原生续聊时，以有来源的交接记录恢复新会话；界面区分「原会话继续」和「从交接恢复」。

执行设置提供默认 CLI、模型和推理强度，阶段设置可覆盖默认值，启动或重试时可只覆盖本轮。选项随执行器支持能力联动；记录请求配置与实际生效配置，不静默降级。首版先验证 Codex CLI，其他执行器后续适配。

运行中的阶段切换配置前先暂停，保留原轮次记录。更换 CLI 时优先依靠任务交接恢复，不能把已有会话标识直接当作其他执行器可用的会话。

## 使用 Orbito 改进 Orbito

后续可从反馈或会话建立改进任务，选择 Orbito 仓库，在独立 worktree 中调研与实现。沿用方案确认、审查与自测，不直接修改当前服务运行目录。

候选版本使用独立实例和端口验证。用户确认合入与切换版本前，保存运行任务交接和配置检查点；切换失败提供恢复路径。涉及存储格式变化时须单独考虑迁移和兼容，不能只依靠代码回退。

第一阶段先提供手动维护途径，自身更新按钮及版本切换机制后续实现；先验证一项由工作台完成自身代码改进的任务，再扩展成完整更新流程。

## 变更与失败

飞书转发、用户主动选取的聊天记录、文档或接口更新均可形成候选变更。需求关联不明确时先选择，结论冲突时先确认。未确认的候选变更不直接修改代码。

变更接入正在运行的任务时，在可确认的停止或阶段交接点重新形成执行依据，不让两个写入 Agent 同时改同一 worktree。

审查与测试记录绑定代码版本。代码继续变化后相关结果可能需要重新执行。循环达到上限、必要环境缺失、需求歧义或方案实质变化时暂停并说明下一步。

## 文档、记忆与换电脑

任务档案保存原始资料的可用快照或引用、当前实现说明、方案、阶段产出、验证证据、决策和交接记录。结构化文件保存机器可读的任务及仓库版本关系；Markdown 保存可阅读的说明。具体格式后续设计。

共享内容存于 Orbito 仓库。运行索引可本地重建；凭据、本机路径和进程状态不作为共享配置。业务代码仍在各自仓库版本化。

在另一台电脑拉取文档和代码后，重新绑定目录、检查 CLI 与授权，再重建 worktree 并启动新的 Agent 会话。未推送的代码和未同步资料不能被视为已可恢复。多仓库同步不是原子操作，应展示各部分是否齐全。

## 第一版验收目标

- 从界面添加数据源，发现一条分配给用户的真实需求；后续可增改来源。
- 整理需求依据，补充接口，选择仓库并确认方案。
- 在独立 worktree 中由 Codex CLI 实现，保留审查与自测证据。
- 通过 UI 分别提交、推送和触发既有部署流程，展示真实反馈。
- 补充一次需求变更并在确认后继续执行。
- 保存任务交接，使另一台已配置的电脑能从已同步检查点继续。

外部服务未完成接入前，原型可以模拟状态，但必须标明模拟，不计为上述真实闭环验收通过。
